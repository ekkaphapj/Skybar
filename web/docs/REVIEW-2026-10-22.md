## ข้อที่ต้องจัดการก่อนย้ายข้อมูลเดิมจริง

พบไฟล์ `TheCottageSkyBar/bin/Debug/Skybar.mdb` และอ่านแบบ `Mode=Read` ได้:

| ตาราง | จำนวนแถว |
|---|---:|
| Items | 95 |
| Stock | 120 |
| Sell | 9,951 |
| Account | 5,955 |
| Cash | 2,235 |
| StockTransaction | 11,638 |

1. **รหัสสินค้าขึ้นต้นด้วยศูนย์ 11 รายการ:** Access เก็บ Items.ID และคอลัมน์ ItemID เป็นข้อความ แต่ D1 เว็บใช้ INTEGER และ API ใช้ Number จึงไม่รักษารหัสบาร์โค้ดเดิม ต้องเปลี่ยน schema/API/หน้าจอให้เก็บรหัสเป็นข้อความก่อนนำเข้าจริง รวมทั้งกำหนดการสร้างรหัสสินค้าอัตโนมัติใหม่ ตรวจไม่ให้รหัสชนกันหลังแปลงชนิดข้อมูล
2. **Stock มี ItemID ซ้ำ 1 กลุ่ม และมี 36 แถวที่ไม่มีสินค้าแม่:** schema เว็บกำหนดหนึ่งแถวต่อ ItemID และ foreign key จึงนำเข้าตรง ๆ ไม่ได้ ต้องตรวจข้อมูลและกำหนดว่าจะรวม แยก หรือเก็บประวัติอย่างไร ห้ามบวกยอดรวมเองโดยไม่ตรวจความหมาย
3. **Account มีบิลรายรับซ้ำ 3 กลุ่ม:** trigger ใหม่ป้องกันบิลซ้ำ จะปฏิเสธการนำเข้าประวัติที่มีบิลซ้ำด้วย ต้องกำหนดวิธีรักษาประวัติและแยกบิลซ้ำจากการป้องกันรายการขายใหม่ก่อนแปลงข้อมูล
4. **Items.Comment ใน Access ยังไม่มีคอลัมน์รองรับในเว็บ:** ต้องกำหนดว่าจะย้ายหมายเหตุไปที่ใด เพื่อไม่ให้ข้อมูลส่วนนี้หาย
5. การนำเข้าในเว็บรองรับ JSON ตาม schema เว็บ ยังไม่ใช่ตัวแปลง `.mdb` โดยตรง ไม่มีการนำ Access เดิมเข้า D1 ในงานตรวจครั้งนี้

ดังนั้นการทำงานหลักของเว็บผ่านกรณีทดสอบ แต่ **ยังไม่ควรย้ายข้อมูลเดิมทั้งหมดเข้า production จนกว่าจะแก้ความต่างของ schema และตรวจยอดหลังแปลง**

## การนำโค้ดแก้ไขไปใช้

มี migration ใหม่ `migrations/0002_sale_guards.sql` ต้อง apply คู่กับโค้ดใหม่ เพื่อให้การป้องกันบิลซ้ำและ Voucher ซ้ำทำงาน ก่อน deploy จริงควรสำรองข้อมูลและจัดการประวัติบิลซ้ำตามข้อข้างต้น

ตอนจบงานตรวจครั้งแรกยังไม่ได้ apply migration ลง remote หรือ deploy ต่อมาผู้ใช้อนุญาตให้ deploy แล้ว และดำเนินการดังนี้:

- สำรอง D1 remote ลง `.backups/pre-deploy-20261022.sql` ก่อนแก้ไข (ไฟล์ไม่อยู่ใน public assets และถูกยกเว้นใน .gitignore)
- Apply `0002_sale_guards.sql` บน remote สำเร็จ ตรวจพบ trigger ทั้งสองตัว
- Deploy ไปยัง https://cottage-skybar-pos.ekapap-j.workers.dev/ สำเร็จ เวอร์ชัน `a93788f5-2e05-47db-bcc3-9a0eb3f9f127`
- ตรวจ SHA-256 ของหน้าเว็บ, JavaScript, CSS และโลโก้จาก URL จริง ตรงกับไฟล์ในเครื่องทั้งสี่ไฟล์
- หน้าเข้าสู่ระบบและโลโก้แสดงบนเว็บจริง และ API ปฏิเสธคำขอที่ยังไม่ล็อกอินด้วย HTTP 401
- PIN ที่ตั้งไว้ในเครื่องใช้ล็อกอินบน production ไม่ได้ จึงไม่ได้ยืนยัน API หลังเข้าสู่ระบบบน production และไม่ได้เปลี่ยน PIN บน production
- ตรวจจำนวนแถวก่อนและหลัง deploy ตรงกัน: Items 4, Stock 4, Sell 5, Account 6, CASH 4, VOUCHER 4 ไม่ได้สร้างรายการขายทดสอบบน production และไม่ได้ย้าย Access เดิมขึ้นไป
